# Firefox / Windows Scaling CSS3D Rendering Post-Mortem

## Summary

The homepage 3D panel navigation in `sky-site` had a Firefox-only rendering and hit-testing bug on Windows when display scaling was above 100%. At 125% scaling, some panels appeared partially clipped after a normal page refresh. The affected regions were not merely visual artifacts: text inside those regions did not render, and clicks in those regions did not interact with the panel.

The issue did not reproduce at 100% Windows display scaling. It was worse at 150% scaling. A hard refresh often avoided the issue, while a normal refresh reproduced it consistently.

The final fix is a small post-load paint invalidation in the library runtime. After initial layout and rendering have had a couple of animation frames to settle, the `SceneGraph` briefly applies a transparent inline outline to the transformed panel elements for one frame. This forces Firefox/WebRender to rebuild the stale CSS3D raster and hit-test bounds without changing the final visual appearance.

## Affected Code

The issue was observed on the homepage panels defined and rendered through:

- `sky-site/src/index.html`
- `sky-site/src/_includes/ZoomPlane.11ty.tsx`
- `sky-site/src/home/home.ts`
- `sky-site/src/home/home.scss`
- `vibe-utils/web-3d-panel-navigation/`
- `sky-site/node_modules/@scupit/web-3d-panel-navigation/`

The retained fix lives in the library runtime:

- `vibe-utils/web-3d-panel-navigation/src/scene-graph.ts`
- `vibe-utils/web-3d-panel-navigation/src/zoom-navigation.ts`

## User-Visible Symptoms

On affected Firefox/Windows configurations:

- The `Projects` and `Games!` panels could render as fully or mostly cut off.
- The `About Me` panel could be clipped along its right edge.
- In some configurations, panel backgrounds were visible but text was missing in the affected area.
- The affected regions were non-interactive, even when their background was visible.
- The issue became more severe with a shorter viewport, such as when Firefox DevTools was docked at the bottom.
- A hard refresh could produce a correct render, while a normal refresh would reproduce the bug again.

That last point was important. It suggested this was not a deterministic layout or camera-framing problem. It looked more like Firefox retaining or reusing stale compositor, raster, or hit-test state across a normal reload.

## Environment Notes

Known reproducing conditions:

- Browser: Firefox on Windows
- Firefox page zoom: 100%
- Windows display scaling: 125% or 150%
- Physical display: 15-inch 1920x1080 screen reproduced the issue
- At Windows display scaling 100%, the issue did not reproduce

Baseline metrics captured at 125% scaling with DevTools docked:

```text

```

The DOM geometry did not explain the clipping. For example, `getBoundingClientRect()` showed the `projects` and `about` panels well inside the viewport, even when Firefox visually clipped them.

## Working Hypothesis

The most likely cause is a Firefox/WebRender bug involving stale visible, raster, or hit-test bounds for CSS3D-transformed DOM elements under non-100% Windows display scaling.

The issue appears to involve the interaction of:

- Windows display scaling and `devicePixelRatio`
- CSS3D transforms generated by the custom Three.js-based CSS3D renderer
- Firefox/WebRender retained display lists or retained hit-test data
- Paint/compositor invalidation timing on normal reload
- Panel visual complexity, including SVG, filters, borders, outlines, shadows, and text

The bug is not just visual paint clipping. Since clicks fail in the same regions where text disappears, Firefox appears to compute an incorrect interactive region as well.

## What Was Ruled Out

Several likely suspects were tested and either ruled out or reduced in importance.

### Camera And Overview Math

Panel `getBoundingClientRect()` values showed that panels were inside the viewport when Firefox clipped them. Earlier geometry checks also projected the panel rectangles correctly for representative viewport sizes.

Conclusion: the camera and overview framing math were not the cause.

### Missing Render Loop

The library renders the CSS3D scene every animation frame through its animation timeline.

Conclusion: this was not a missing initial render.

### The WebGL Skybox

The skybox was temporarily disabled. The clipping and noninteractive regions still occurred.

Conclusion: the WebGL layer behind the CSS3D scene was not required to trigger the bug.

### The Content Reveal Layer

The `#page-content-container` layer was temporarily disabled, including its `clip-path`. The issue still occurred.

Conclusion: the hidden/clipped content overlay was not the primary cause in overview mode.

### CSS3D Renderer Root Overflow

Changing the CSS3D renderer root from `overflow: hidden` to `overflow: visible` did not fix the issue.

Conclusion: root overflow was not sufficient as a workaround.

### CSS3D Object Scale

The library default `scale` was changed from `0.5` to `1`. The same missing and noninteractive regions still occurred.

Conclusion: object-level CSS matrix scaling was not the main trigger.

### `transform-style: preserve-3d`

Temporarily changing the renderer camera element from `preserve-3d` to `flat` did not resolve the issue.

Conclusion: `preserve-3d` may still be part of Firefox's fragile path, but simply flattening that element was not a useful fix.

### SVG Alone

Removing, hiding, or restoring the SVG frame changed the presentation, but did not fully explain the bug. Later testing showed the original SVG frame and drop-shadow filters could be restored safely once the post-load invalidation was added.

Conclusion: SVG and filters increased suspicion, but they were not the root cause.

## Important Discovery

A minimal plain-panel configuration could render correctly after a hard refresh, but still fail after a normal refresh. This happened even after timestamp-versioning local CSS and JavaScript assets, and even in a new tab or private window.

That behavior made stale local assets unlikely. It pointed instead toward Firefox/WebRender retaining or reconstructing an incorrect CSS3D layer state on normal reload.

## Final Fix

The retained workaround is a one-frame raster refresh after the navigation initializes.

In `vibe-utils/web-3d-panel-navigation/src/zoom-navigation.ts`, `ZoomPlaneNavigator` schedules the refresh after its scene, camera, event handlers, and optional URL hash reconciliation are initialized:

```ts
this.sceneGraph.schedulePostLoadRasterRefresh();
```

In `vibe-utils/web-3d-panel-navigation/src/scene-graph.ts`, the library waits two animation frames, briefly applies a transparent inline outline to each transformed panel element, then restores each element's previous inline outline:

```ts
schedulePostLoadRasterRefresh(): void {
  this.queueAnimationFrame(() => {
    this.queueAnimationFrame(() => {
      this.forceRasterRefresh();
    });
  });
}
```

The outline is only present for one frame. It does not alter the final visual state, layout, or interaction model. Its purpose is to force Firefox to repaint and rebuild the affected CSS3D panel bounds after initial layout. The implementation uses inline styles instead of a package stylesheet rule so the fix still applies for consumers that customize or replace the default stylesheet.

## Why This Fix Is Acceptable

The workaround is deliberately small and local:

- It applies to all `ZoomPlaneNavigator` consumers after initialization.
- It does not change the public package API.
- It does not change final visual styling.
- It does not depend on browser sniffing.
- It keeps the original SVG frame, filters, skybox, text, and content reveal behavior intact.
- It addresses both visual clipping and hit-testing failure.

The fix is not a true root-cause repair inside Firefox/WebRender. It is a pragmatic invalidation nudge for a browser compositor bug.

## Verification

The final restored configuration was tested in Firefox at 125% Windows display scaling with a normal refresh:

- Original SVG frame restored
- SVG drop-shadow filters restored
- Hover filters restored
- Text shadow restored
- WebGL skybox restored
- Content reveal layer restored
- Panel click navigation restored
- No visible clipping
- No noninteractive panel regions
- Panel content reveals normally

Lint checks reported no issues for the edited source files.

## Lessons Learned

The most misleading part of the bug was that several visual simplifications appeared to help temporarily, but the normal-refresh versus hard-refresh difference showed that the browser's retained rendering state mattered as much as the current CSS.

Future debugging of similar CSS3D Firefox issues should check:

- Regular refresh versus hard refresh
- Windows display scaling values
- `window.devicePixelRatio`
- Panel `getBoundingClientRect()` versus visible paint
- Paint visibility versus hit-test behavior
- Whether a harmless post-load style invalidation repairs the scene

If a harmless invalidation fixes both rendering and hit-testing, the problem is likely below application layout code and inside the browser's compositor or retained display-list path.

## Future Follow-Up

The fix is currently unconditional because the failure affects Firefox clients broadly enough that all library consumers should get the safer initialization behavior by default.

If this ever causes an unexpected regression, a future version could make the refresh configurable with an option such as:

```ts
new ZoomPlaneNavigator(refs, {
  postLoadRasterRefresh: true,
});
```

For now, no option is exposed because the refresh is short-lived, visually inert, and fixes a real rendering failure for affected Firefox users.
