Guide 03 — Linear Interpolation and Easing

Curriculum for web-3d-panel-navigation. Prerequisites: Guide 01 (vectors) and Guide 02 (trig).

1. Why this matters

Almost every visible animation in this package — the camera arc when you click a panel, the clip-path that opens to reveal a section, the panel that fades to nothing as the page materialises — is a value gradually changing from a "before" number to an "after" number. The mathematical operation that defines what "gradually" means is linear interpolation (lerp), and the curve that bends the time axis so the motion looks alive instead of mechanical is an easing function. The library exposes two ease curves and one phase utility in src/easing.ts (lines 8–19 and 34–38), a smoothstep private to src/camera-transitions.ts (lines 20–24), and a vector-style lerp on screen rectangles in src/projection.ts (lerpScreenRect, lines 215–226). The orchestrator at src/zoom-navigation.ts (lines 200–218 and 331–349) chains all three together to drive two overlapping animation phases (camera + clip) on a single shared progress timeline. Once this guide clicks, those files become a 30-second read.

2. Building intuition

2.1 The number line and the parameter \(t\)

Picture a number line with two endpoints, \(a\) and \(b\). Think of \(a\) as "where we are now" and \(b\) as "where we want to be". Pick any point between them. How would you describe its position with a single number?

The cleanest answer is a fraction: how far along the way from \(a\) to \(b\) am I? Call that fraction \(t\). When \(t = 0\) we are sitting exactly on \(a\). When \(t = 1\) we have arrived at \(b\). When \(t = 0.5\) we are halfway. \(t\) is unitless — a pure progress dial, ranging over \([0, 1]\).

The position itself is then $$ p(t) = a + (b - a)\, t. $$ Read it as start at \(a\), then move \(t\) of the distance toward \(b\). The factor \((b - a)\) is the displacement; \(t\) selects how much of it to apply. That is lerp in one line.

2.2 Promoting it to vectors

A 3D position is just a triple of numbers. There is nothing special about doing the same recipe to each component independently: $$ \mathbf{p}(t) = \mathbf{a} + (\mathbf{b} - \mathbf{a})\, t = \big(a_x + (b_x - a_x) t,\; a_y + (b_y - a_y) t,\; a_z + (b_z - a_z) t\big). $$ Three.js exposes this exact operation as new THREE.Vector3().lerpVectors(from, to, t). Geometrically, the result traces the straight line segment from \(\mathbf{a}\) to \(\mathbf{b}\). Lerp on vectors is the "straight-shot" path between two points — the boring, default route.

2.3 Why straight-shot motion looks bad in real animations

Linear motion in time is what a robot does. Real objects accelerate from rest and decelerate to rest. So even though the path is a straight line in 3D, the schedule along that path should not be linear — we want a slow start, fast middle, slow end. The trick is to distort the parameter \(t\) before feeding it into lerp: $$ \mathbf{p}(t) = \mathrm{lerp}\big(\mathbf{a},\, \mathbf{b},\, f(t)\big). $$ The function \(f\) is the ease curve. As long as \(f(0) = 0\) and \(f(1) = 1\), the start and end positions are unchanged — only the in-between speed changes. This is the secret of all the camera transitions in this codebase.

3. The math

3.1 Scalar lerp and an algebraic identity

We defined \(\mathrm{lerp}(a, b, t) = a + (b - a)\, t\). There is an equivalent form that some codebases prefer: $$ \mathrm{lerp}(a, b, t) = (1 - t)\, a + t\, b. $$ These are the same function. To prove it, expand the right-hand side: $$ (1 - t) a + t b = a - t a + t b = a + t(b - a). $$ That is the "weighted blend" reading: the result is a convex combination of \(a\) and \(b\) with weights \((1 - t)\) and \(t\) that always sum to 1. The weighted-blend form is what gives geometric meaning to interpolation on vectors that lie on curves (e.g. quaternions, where the naive form would not preserve unit length — see Guide 10).

3.2 Clamp

Animation parameters tend to stray outside \([0, 1]\) for boring reasons: floating-point drift, phase boundaries that round in the wrong direction, callers that pass a global progress value to a sub-phase that is not yet active. The standard fix is the clamp: $$ \mathrm{clamp}(x, \ell, h) = \max\!\big(\ell,\; \min(h, x)\big). $$ Read it as: "if \(x\) is below the floor, return the floor; if above the ceiling, return the ceiling; otherwise pass through." Three.js gives us THREE.MathUtils.clamp; the codebase calls it explicitly inside smoothstep at line 22 of camera-transitions.ts: 

const t = THREE.MathUtils.clamp((x - edge0) / (edge1 - edge0), 0, 1);

3.3 Remap, derived

Suppose you have a global timeline \(t \in [0, 1]\) and a sub-phase that runs from \(s\) to \(e\) within it (with \(0 \le s < e \le 1\)). You want a local progress that is 0 when the global progress hits \(s\) and 1 when it hits \(e\). Linear scaling does it: $$ \tau(t) = \frac{t - s}{e - s}. $$ Verify the endpoints: at \(t = s\) the numerator is zero, so \(\tau = 0\). At \(t = e\) numerator equals denominator, so \(\tau = 1\). Outside the interval \(\tau\) flies off to \(\pm\infty\), which is meaningless for a phase — so we clamp: $$ \mathrm{remap}(t, s, e) = \mathrm{clamp}\!\Big(\tfrac{t - s}{e - s},\, 0,\, 1\Big). $$ The implementation in src/easing.ts (lines 34–38) inlines the clamp via two short-circuit branches: 

export function remap(t: number, start: number, end: number): number {
  if (t <= start) return 0;
  if (t >= end) return 1;
  return (t - start) / (end - start);
}

That early-exit style is faster than computing then clamping, and it sidesteps the divide-by-zero edge case if a caller ever passes start === end (the second if catches it before division).

3.4 The cubic ease-out

We want a curve \(f\) on \([0, 1]\) with \(f(0) = 0\), \(f(1) = 1\), that starts fast and decelerates. The simplest closed form is to take "1 minus a cube of the distance to the finish": $$ \mathrm{easeOutCubic}(t) = 1 - (1 - t)^3. $$ Check the boundaries. At \(t = 0\): \(1 - 1^3 = 0\). At \(t = 1\): \(1 - 0^3 = 1\). Now look at the slope. Let \(u = 1 - t\), so \(f = 1 - u^3\) and \(f'(t) = -3u^2 \cdot \frac{du}{dt} = 3(1 - t)^2.\) At \(t = 0\) the slope is \(3\) — three times faster than linear. At \(t = 1\) it is \(0\): the motion stops smoothly. That is exactly the "quick start, soft landing" feel.

3.5 The cubic ease-in-out, piecewise

We want a curve that is symmetric: slow start, fast middle, slow end. The codebase implements the standard piecewise cubic from src/easing.ts lines 8–12: 

export function easeInOutCubic(t: number): number {
  return t < 0.5
    ? 4 * t * t * t
    : 1 - Math.pow(-2 * t + 2, 3) / 2;
}

Where do those magic numbers come from? Build the function up. On the first half \([0, 0.5]\) we want an ease-in cubic that goes from 0 to 0.5. The basic ease-in cubic on \([0, 1]\) is \(g(t) = t^3\). We compress its domain to \([0, 0.5]\) by feeding it \(2t\) instead of \(t\), and then squash its range back into \([0, 0.5]\) by halving: $$ f_1(t) = \tfrac{1}{2}\, (2t)^3 = 4 t^3 \quad \text{for } t \in [0, 0.5]. $$ On the second half \([0.5, 1]\) we want the mirror image: an ease-out cubic that goes from 0.5 to 1. The mirror of \(t^3\) across the midpoint is the substitution \(t \mapsto 1 - t\), giving \(1 - (1 - t)^3\), then we compress and shift to fit \([0.5, 1]\). Applying the same \((2t - 1)\) reparameterisation, halving, and offsetting gives $$ f_2(t) = 1 - \tfrac{1}{2}\,(-2t + 2)^3 \quad \text{for } t \in [0.5, 1]. $$ That is precisely what the code computes. Continuity check at the seam \(t = 0.5\): \(f_1(0.5) = 4 \cdot 0.125 = 0.5\), and \(f_2(0.5) = 1 - \tfrac{1}{2} \cdot 1^3 = 0.5\). They agree, so the function is \(C^0\).

Smoothness check. \(f_1'(t) = 12 t^2\), so \(f_1'(0.5) = 12 \cdot 0.25 = 3\). For \(f_2\), differentiate via the chain rule on \(u = -2t + 2\): \(f_2'(t) = -\tfrac{1}{2} \cdot 3 u^2 \cdot (-2) = 3 u^2 = 3(-2t + 2)^2\). At \(t = 0.5\): \(3 \cdot 1^2 = 3\). The slopes match, so the function is also \(C^1\) — the velocity has no visible kink at the midpoint.

3.6 Smoothstep, derived from first principles

The smoothstep used at camera-transitions.ts lines 20–24 is a different cubic: $$ \mathrm{smoothstep}(t) = t^2 (3 - 2t) = 3 t^2 - 2 t^3. $$ We can derive it as the unique cubic polynomial \(p(t) = a + b t + c t^2 + d t^3\) satisfying four constraints: $$ p(0) = 0, \quad p(1) = 1, \quad p'(0) = 0, \quad p'(1) = 0. $$ The first gives \(a = 0\). The third (\(p'(t) = b + 2 c t + 3 d t^2\)) gives \(b = 0\), so the polynomial reduces to \(p(t) = c t^2 + d t^3\). The second is \(c + d = 1\). The fourth is \(2 c + 3 d = 0\), i.e. \(c = -\tfrac{3}{2} d\). Substituting: \(-\tfrac{3}{2} d + d = 1 \Rightarrow -\tfrac{1}{2} d = 1 \Rightarrow d = -2\) and \(c = 3\). So \(p(t) = 3 t^2 - 2 t^3 = t^2(3 - 2t)\). That is a real derivation, not a hand-wave. The two horizontal-slope endpoints make smoothstep ideal for blending between two regimes where any velocity discontinuity at the boundary would be visible.

The full smoothstep(edge0, edge1, x) in the codebase composes this with a remap-then-clamp so the curve only bites between the two edges: 

function smoothstep(edge0: number, edge1: number, x: number): number {
  const t = THREE.MathUtils.clamp((x - edge0) / (edge1 - edge0), 0, 1);
  return t * t * (3 - 2 * t);
}

3.7 Smoothstep vs ease-in-out: not the same curve

Both are S-shaped, both are zero-slope at the ends, both are symmetric about \((0.5, 0.5)\). They are not equal. Compare numerically:

\(t\)\(\mathrm{easeInOutCubic}(t)\)\(\mathrm{smoothstep}(t)\)difference
0.25\(4(0.25)^3 = 0.0625\)\(0.0625 \cdot 2.5 = 0.15625\)0.09375
0.50\(0.5\)\(0.25 \cdot 2 = 0.5\)0
0.75\(1 - \tfrac{1}{2}(0.5)^3 = 0.9375\)\(0.5625 \cdot 1.5 = 0.84375\)0.09375

At \(t = 0.5\) they agree exactly. Off the midpoint they diverge by up to about \(0.094\) — about a 9% positional difference. easeInOutCubic is steeper through the middle (slope \(3\) at the seam) than smoothstep (slope \(1.5\)). So the codebase uses easeInOutCubic for camera motion, where a snappier feel through the middle is good, and smoothstep for a gentler clip reveal and for the regime-blending threshold around 30°–35° (line 79).

4. In this codebase

4.1 Vector lerp and FOV lerp side-by-side

From src/camera-transitions.ts lines 9–18:

function lerpUpAndFov(
  from: CameraState,
  to: CameraState,
  t: number
): { up: THREE.Vector3; fov: number } {
  const up = new THREE.Vector3().lerpVectors(from.up, to.up, t).normalize();
  const fov = from.fov + (to.fov - from.fov) * t;
  return { up, fov };
}

Two operations, one parameter. The vector lerp is the componentwise version of section 2.2, followed by a normalisation that pulls the result back onto the unit sphere (lerp of two unit vectors does not stay unit-length — see Guide 10 for the proper fix, slerp). The FOV lerp is the literal scalar form \(\mathrm{fov}(t) = \mathrm{fov}_{\text{from}} + (\mathrm{fov}_{\text{to}} - \mathrm{fov}_{\text{from}})\, t\).

4.2 Lerp on a screen rectangle

From src/projection.ts lines 215–226:

export function lerpScreenRect(
  from: ScreenRect,
  to: ScreenRect,
  t: number
): ScreenRect {
  return {
    top: from.top + (to.top - from.top) * t,
    right: from.right + (to.right - from.right) * t,
    bottom: from.bottom + (to.bottom - from.bottom) * t,
    left: from.left + (to.left - from.left) * t
  };
}

A ScreenRect here is just a 4-tuple of pixel insets. So this is a 4-component lerp, identical in spirit to a vector lerp — the only reason it is not literally Vector4-flavoured is that the field names are domain-meaningful. Each component is the scalar form \(a + (b - a)\, t\). When this gets called during a zoom, the rectangle "breathes" smoothly from the panel's tight bounding rect to the full viewport.

4.3 Easing applied on top of a lerp

From src/camera-transitions.ts lines 101–109 (the Early-Look branch):

const posT = easeInOutCubic(rawT);

// Target uses a faster curve — arrives at ~70% of the animation
const targetRaw = Math.min(rawT / 0.7, 1.0);
const targetT = easeOutCubic(targetRaw);

const position = new THREE.Vector3().lerpVectors(from.position, to.position, posT);
const target = new THREE.Vector3().lerpVectors(from.target, to.target, targetT);
const { up, fov } = lerpUpAndFov(from, to, posT);

Two parallel motions on one shared timeline, but on different schedules:

  • Position uses easeInOutCubic(rawT) — symmetric S-curve over the full duration.
  • Target (the look-at point) uses a remap-then-easeOutCubic that finishes at \(\mathrm{rawT} = 0.7\). The expression Math.min(rawT / 0.7, 1.0) is exactly \(\mathrm{remap}(\mathrm{rawT}, 0, 0.7)\) without the lower clamp (since rawT is already non-negative).

So the camera looks at the destination 30% of the way before it actually arrives there. That is purely an easing trick and is what creates the cinematic "lead with your eyes" feel.

4.4 Easing applied to the orbit branch

From src/camera-transitions.ts lines 124–130:

const t = easeInOutCubic(rawT);

// Linearly interpolate the look-at target
const target = new THREE.Vector3().lerpVectors(from.target, to.target, t);

// For position: slerp around the midpoint of the two targets
const midTarget = new THREE.Vector3().lerpVectors(from.target, to.target, 0.5);
const fromOffset = new THREE.Vector3().subVectors(from.position, midTarget);
const toOffset = new THREE.Vector3().subVectors(to.position, midTarget);

Same eased \(t\), used for both target lerp and (further down, on the offset vectors) for the direction slerp. The target gets a linear lerp on the eased \(t\); the position vector gets a slerp (Guide 10) on the same eased \(t\). The point: the easing sits one layer above the actual interpolation primitive and is reusable across both lerp and slerp.

4.5 Phase composition with remap (the conductor)

From src/zoom-navigation.ts lines 200–218 — the orchestrator that drives a single global progress through two overlapping phases:

const { promise, cancel } = this.timeline.runSequence(totalDuration, (progress) => {
  const rawCameraT = remap(progress, 0, cameraEnd);
  this.cameraController.setToState(
    calculateTransitionState(startCameraState, targetCameraState, rawCameraT)
  );

  if (progress >= clipStart) {
    const clipRaw = remap(progress, clipStart, 1.0);
    const clipT = clipRaw * clipRaw * (3 - 2 * clipRaw);
    const currentRect = lerpScreenRect(planeRect, targetRect, clipT);
    this.clipController.setClipRect(currentRect);
    this.clipController.setOpacity(clipT);
  }

  if (progress >= clipStart) {
    const fadeT = remap(progress, clipStart, planeFadeEnd);
    this.sceneGraph.setPlaneOpacity(planeId, 1 - fadeT);
  }
});

This block is the whole point of having remap in the package. There is one global progress in \([0, 1]\) but three things happening on three different sub-intervals:

  • Camera reorientation runs over \([0,\,\mathrm{cameraEnd}]\). remap(progress, 0, cameraEnd) stretches that sub-window back out to \([0, 1]\) so the camera transition can be written without knowing it lives inside a larger timeline.
  • Clip-path reveal runs over \([\mathrm{clipStart}, 1]\). The remap'd value is then run through smoothstep inline — note clipRaw * clipRaw * (3 - 2 * clipRaw) on line 208, which is exactly \(t^2(3 - 2t)\) without the function call.
  • Plane fade-out runs over \([\mathrm{clipStart},\,\mathrm{planeFadeEnd}]\), again via remap.

The mirror image lives at src/zoom-navigation.ts lines 331–349, the zoom-out flow, which uses the same building blocks in the opposite order.

6. Worked examples

Example 6.1 — Camera position halfway through a zoom-in

Suppose the overview camera position is \(\mathbf{a} = (0, 0, 50)\) and the perpendicular state for a clicked panel is \(\mathbf{b} = (12, 4, 18)\). The orchestrator at line 200 of zoom-navigation.ts sends a global progress in \([0, 1]\) into remap(progress, 0, cameraEnd). Suppose cameraEnd = 0.6 and progress = 0.45. Where is the camera?

Step 1 — local progress: $$ \mathrm{rawCameraT} = \frac{0.45 - 0}{0.6 - 0} = 0.75. $$ Step 2 — ease (Early-Look branch picks easeInOutCubic for position): $$ \mathrm{posT} = 1 - \tfrac{1}{2}(-2 \cdot 0.75 + 2)^3 = 1 - \tfrac{1}{2}(0.5)^3 = 1 - 0.0625 = 0.9375. $$ Step 3 — vector lerp: $$ \mathbf{p} = \mathbf{a} + (\mathbf{b} - \mathbf{a}) \cdot 0.9375 = (0, 0, 50) + (12, 4, -32) \cdot 0.9375 = (11.25,\, 3.75,\, 20). $$ At only 45% of the global timeline the camera is already 93.75% of the way to its target because cameraEnd compresses the camera phase into the first 60% and easeInOutCubic rushes the middle.

Example 6.2 — Clip rectangle a third of the way through the reveal

Pick numbers from the codebase pattern. The plane bounding rect is \(R_a = \{ \mathrm{top:}120,\, \mathrm{right:}200,\, \mathrm{bottom:}120,\, \mathrm{left:}200 \}\) (pixels) and the target rect is the full viewport, \(R_b = \{0, 0, 0, 0\}\). Suppose clipStart = 0.5 and progress = 0.7. What clip rect does the controller receive?

Step 1 — local progress via remap: $$ \mathrm{clipRaw} = \frac{0.7 - 0.5}{1 - 0.5} = 0.4. $$ Step 2 — smoothstep (line 208 inlines \(t^2(3 - 2t)\)): $$ \mathrm{clipT} = 0.4^2 \cdot (3 - 2 \cdot 0.4) = 0.16 \cdot 2.2 = 0.352. $$ Step 3 — componentwise lerp via lerpScreenRect: $$ \mathrm{top} = 120 + (0 - 120) \cdot 0.352 = 120 - 42.24 = 77.76. $$ By symmetry the other three components compute the same way: \(\mathrm{right} = 200 - 70.4 = 129.6\), \(\mathrm{bottom} = 77.76\), \(\mathrm{left} = 129.6\). The reveal has eaten about 35% of the inset on each side.

Example 6.3 — Where does the regime blend lock in to "orbit"?

At line 79 of camera-transitions.ts the blend value is \(\mathrm{smoothstep}(30°,\, 35°,\, \theta)\) where \(\theta\) is the total reorientation (forward angle plus up angle, in radians). At what \(\theta\) does blend = 0.5 exactly?

Smoothstep crosses 0.5 at the midpoint of its remap interval. Inside smoothstep, the inner local \(t\) reaches 0.5 when \((\theta - 30°)/(35° - 30°) = 0.5\), i.e. \(\theta = 32.5°\). At that local \(t\) the cubic returns \(0.25 \cdot 2 = 0.5\). So the regime flips from "Early Look" to "Orbit" exactly at \(\theta = 32.5°\) of total reorientation. Note this is not halfway between 30° and 35° in any deep sense — it just happens that \(t^2(3 - 2t)\) is symmetric about \(t = 0.5\), so its midpoint output equals 0.5.

  3. Phase compression. The orchestrator computes cameraEnd = cameraDuration / totalDuration. If cameraDuration = 800ms, clipDuration = 600ms and overlapRatio = 0.4, compute totalDuration, cameraEnd, and clipStart using the formulas at lines 193–196 of zoom-navigation.ts.

9. Appendix: Solutions

Solution to 7.1 — Endpoint and slope check for easeOutCubic.

\(\mathrm{easeOutCubic}(0) = 1 - (1 - 0)^3 = 1 - 1 = 0\). \(\mathrm{easeOutCubic}(1) = 1 - 0^3 = 1\). The derivative is \(f'(t) = 3(1 - t)^2\) (chain rule on \((1 - t)^3\)). At \(t = 0\), \(f'(0) = 3 \cdot 1 = 3\). At \(t = 1\), \(f'(1) = 3 \cdot 0 = 0\). The motion launches at three times linear speed and coasts to a perfect halt.

Solution to 7.2 — Equivalence of the two lerp forms.

\((1 - t) a + t b = a - t a + t b = a + t(b - a) = a + (b - a) t.\) Both forms compute the same scalar. They are not interchangeable on quaternions (or any non-flat manifold) because the first form blends weights that always sum to 1 — a convex combination is a well-defined geometric operation on the right kinds of spaces. The second form involves subtracting two unit quaternions and adding the result to a unit quaternion, which leaves the unit sphere immediately. Slerp (Guide 10) restores the geometry.

Solution to 7.3 — Phase compression numbers.

From line 194: \(\mathrm{totalDuration} = 800 + 600 \cdot (1 - 0.4) = 800 + 360 = 1160\) ms. Line 195: \(\mathrm{cameraEnd} = 800 / 1160 \approx 0.6897\). Line 196: \(\mathrm{clipStart} = 0.6897 - (0.4 \cdot 600 / 1160) = 0.6897 - 0.2069 \approx 0.4828\). So the clip phase opens at about 48% of the global timeline and the camera phase ends at about 69%. The 20.7% overlap is exactly the overlapRatio-weighted clip share.

Solution to 7.4 — Out-of-range remap input.

With progress = 1.05, line 36 (if (t >= end) return 1;) fires immediately because \(1.05 \ge 1.0\). The function returns 1 without ever reaching the division. That is the inlined upper-clamp branch; the lower branch (line 35) handles the symmetric case. So remap is total and never produces a value outside \([0, 1]\) even on bad input.

Solution to 7.5 — Endpoint slopes of smoothstep, without calculus.

Section 3.6 derived \(p(t) = t^2(3 - 2t)\) as the unique cubic satisfying \(p(0) = 0\), \(p(1) = 1\), \(p'(0) = 0\), \(p'(1) = 0\). Two of those four constraints are exactly the slope conditions we are asked to verify, so they are baked in by construction — the function would not be the smoothstep cubic if they failed. We chose the coefficients \(c = 3\), \(d = -2\) precisely because those slopes had to be zero.

Solution to 7.6 — Numeric divergence at t = 0.1 and 0.9.

\(\mathrm{easeInOutCubic}(0.1) = 4 \cdot 0.001 = 0.004\). \(\mathrm{smoothstep}(0.1) = 0.01 \cdot 2.8 = 0.028\). Difference \(\approx 0.024\). At \(t = 0.9\): \(\mathrm{easeInOutCubic}(0.9) = 1 - \tfrac{1}{2}(0.2)^3 = 0.996\). \(\mathrm{smoothstep}(0.9) = 0.81 \cdot 1.2 = 0.972\). Difference \(\approx 0.024\). easeInOutCubic is closer to 0 longer near the start and closer to 1 longer near the end — its middle is steeper (its midpoint slope is 3 versus smoothstep's 1.5), so it feels snappier through the middle of the animation while still ending soft.

Solution to 7.7 — Linear vs eased rect lerp.

Linear at \(t = 0.25\): top \(= 60 + (0 - 60) \cdot 0.25 = 45\), and similarly \(\{\mathrm{top:}45, \mathrm{right:}60, \mathrm{bottom:}45, \mathrm{left:}60\}\). With easeOutCubic(0.25) = 1 - 0.75^3 = 1 - 0.421875 = 0.578125\), the rect becomes \(\{\mathrm{top:} 60 \cdot (1 - 0.578) = 25.31, \mathrm{right:} 33.75, \mathrm{bottom:} 25.31, \mathrm{left:} 33.75\}\). The eased version reaches the destination much faster early on, so on screen the panel "snaps open" instead of unrolling at constant speed — that is what easeOutCubic is for.

Solution to 7.8 — Build easeInCubic.

Conditions: \(f(0) = 0\), \(f(1) = 1\), \(f'(0) = 0\), \(f'(1) = 3\). The natural candidate is \(f(t) = t^3\). Check: \(0^3 = 0\), \(1^3 = 1\), derivative \(3t^2\) gives \(0\) at the start and \(3\) at the end. All four conditions hold. Reflecting easeOutCubic via the standard "inverse easing" identity \(g(t) = 1 - f(1 - t)\): with \(\mathrm{easeOutCubic}(t) = 1 - (1 - t)^3\), the in/out reflection is \(\mathrm{easeInCubic}(t) = 1 - \mathrm{easeOutCubic}(1 - t) = 1 - (1 - (1 - (1 - t))^3) = 1 - (1 - t^3) = t^3\). Same answer.

Solution to 7.9 — Smoothstepped fade.

The rewrite would read: 

const fadeRaw = remap(progress, clipStart, planeFadeEnd);
const fadeT = fadeRaw * fadeRaw * (3 - 2 * fadeRaw);
this.sceneGraph.setPlaneOpacity(planeId, 1 - fadeT);

Why the codebase prefers the linear remap: the fade window [clipStart, planeFadeEnd] is intentionally short (about 8% of the timeline). At the very start of that window the clip reveal has just begun — and a smoothstepped fade would barely move from opacity 1 for the first half of those 8%, leaving the plane visibly "stuck" while the section content already starts appearing through the clip. Linear remap starts moving immediately and finishes quickly, which is the right behaviour for a tiny crossover window. Easing only pays off when the duration is long enough for the slow-start to be felt as motion rather than as latency.
