Guide 13 — Shader Math: Gradients and Falloff

Curriculum for web-3d-panel-navigation. Prerequisites: Guide 01 (vectors, dot product), Guide 03 (lerp, smoothstep).

1. Why this matters

So far the curriculum has been about geometry: where panels go, how they tile, how vectors point. This guide shifts to shading — the GLSL code that decides what color each pixel ends up. Two pieces of project shader code drive everything in this guide:

  • The skybox gradient. In src/skybox/gradient-mesh.ts there's a 12-line GLSL fragment shader that paints a smooth three-color gradient across the inside of a cube the camera sits in. That gradient is the soft, painted-looking sky behind your panels.
  • The starfield's per-star falloff. In src/skybox/starfield-skybox.ts (lines 56–60), each star is a square point sprite that's softened into a circle by a single smoothstep call. That one line is the difference between “pixelated dots” and “little glowing stars.”

The starfield also contains the gradient mesh as its background, so the same gradient math reappears there. We cover both shaders in one guide because they share the same vocabulary: a tiny bit of GLSL syntax, the dot product (Guide 01), and lerp / smoothstep (Guide 03).

By the end you'll be able to read those shaders the way you'd read a JS function: not as magic, but as a short list of arithmetic steps you've already studied.

2. GLSL primer (just enough)

GLSL is a C-flavored language that runs on the GPU. Three.js compiles a ShaderMaterial's strings into a vertex shader and a fragment shader, then runs them in parallel for every vertex and every covered pixel.

The two stages

  • Vertex shader. Runs once per vertex of your geometry. Its job is to set gl_Position — the 4-component clip-space position. It can also write varyings, which the GPU interpolates across the triangle and hands to the fragment shader.
  • Fragment shader. Runs once per pixel covered by a triangle. Its job is to set gl_FragColor — an RGBA color. It reads the interpolated varyings and any uniforms.

Three kinds of input

  • Uniform — a value set per draw call from JavaScript (a color, a time, a direction). Constant across every vertex and every fragment of that draw.
  • Attribute — per-vertex data (position, a custom aBrightness, etc.). Only the vertex shader sees attributes directly.
  • Varying — declared in both shaders. The vertex shader writes it; the GPU linearly interpolates it across the triangle; the fragment shader reads the interpolated value.

Types and built-ins you'll see

The skybox shaders use only a handful:

  • vec3 — a 3-component float vector. Holds positions, directions, RGB colors. Component access: v.x, v.y, v.z, or v.r, v.g, v.b.
  • vec4 — 4 components. Used for clip-space position and RGBA color.
  • vec2 — 2 components. gl_PointCoord is one (the per-fragment UV inside a point sprite, ranging from (0,0) top-left to (1,1) bottom-right).
  • dot(a, b) — same dot product as Guide 01. Returns a scalar.
  • length(v) — Euclidean magnitude $\lVert\mathbf{v}\rVert$.
  • normalize(v) — v / length(v).
  • mix(a, b, t) — linear interpolation, defined as $\mathbf{a}(1 - t) + \mathbf{b}\,t$. This is GLSL's name for lerp; it's exactly the function from Guide 03, just usually applied to vec3 colors. It works component-wise.
  • smoothstep(edge0, edge1, x) — the cubic Hermite ramp from Guide 03. Returns 0 below edge0, 1 above edge1, and a smooth $C^1$ S-curve in between.

A tiny solid-color example

Before reading the project shaders, here's the smallest possible vertex/fragment pair, just for orientation:

// Vertex shader
void main() {
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
}

// Fragment shader
precision mediump float;
void main() {
  gl_FragColor = vec4(1.0, 0.5, 0.2, 1.0); // solid orange
}

Three.js automatically declares position (an attribute), projectionMatrix, and modelViewMatrix (uniforms) for you. That's why the project shaders use them without declaration.

3. The math

3.1 Directional gradient via dot product

Imagine you're inside a cube, looking around. Each fragment on the cube's inner wall has a 3D direction $\mathbf{d}$ — the unit vector from the cube's center to that fragment's world position. We want the color to depend smoothly on which way the fragment is facing, so that one side of the sky is color A, the opposite side is color C, and the middle is color B.

Pick a gradient axis $\hat{\mathbf{u}}$ — for instance, “up.” The natural way to ask “how aligned is fragment direction $\hat{\mathbf{d}}$ with axis $\hat{\mathbf{u}}$?” is the dot product:

\[ \hat{\mathbf{d}} \cdot \hat{\mathbf{u}} = \cos\theta \in [-1, 1] \]

where $\theta$ is the angle between them (Guide 01). This value is $+1$ when the fragment is at the top, $-1$ at the bottom, and $0$ on the equator.

We need a parameter in $[0, 1]$ to feed into a color mix. The cheapest fix is the affine remap:

\[ t = \tfrac{1}{2}(\hat{\mathbf{d}} \cdot \hat{\mathbf{u}}) + \tfrac{1}{2} \]

Plug in the endpoints to confirm: $-1 \mapsto 0$, $+1 \mapsto 1$, $0 \mapsto 0.5$. The remapping is linear, so equal angular steps near the equator cover roughly equal $t$-intervals near 0.5, which is exactly what you want for a sky gradient: the brightest band sits at the top, the darkest at the bottom, with a smooth horizon in the middle.

In GLSL this is one line:

float t = dot(normalize(vDirection), normalize(uDirection)) * 0.5 + 0.5;
Why normalize twice? The dot product equals $\cos\theta$ only when both vectors are unit-length (Guide 01). The varying vDirection comes from interpolated cube-vertex positions, which are nowhere near unit length on the cube faces; uDirection is whatever the user passed in (default (1.0, 0.6, 0.4), length $\approx 1.23$). Both must be normalized.

3.2 Three-stop piecewise color mix

A single lerp $\operatorname{mix}(\mathbf{c}_A, \mathbf{c}_B, t)$ gives a two-color gradient. For three colors, the project splits the $[0, 1]$ range in half:

\[ \mathbf{c}(t) = \begin{cases} \operatorname{mix}(\mathbf{c}_A, \mathbf{c}_B, 2t) & 0 \le t < \tfrac{1}{2} \\[2pt] \operatorname{mix}(\mathbf{c}_B, \mathbf{c}_C, 2(t - \tfrac{1}{2})) & \tfrac{1}{2} \le t \le 1 \end{cases} \]

The factor of 2 stretches each half-range back to $[0, 1]$ so that each mix sees a full lerp parameter.

Continuity check at $t = 1/2$. The left branch evaluates to $\operatorname{mix}(\mathbf{c}_A, \mathbf{c}_B, 1) = \mathbf{c}_B$. The right branch evaluates to $\operatorname{mix}(\mathbf{c}_B, \mathbf{c}_C, 0) = \mathbf{c}_B$. They agree, so $\mathbf{c}(t)$ is $C^0$ continuous — no visible seam.

Slope check. Differentiate component-wise:

\[ \frac{d\mathbf{c}}{dt} = \begin{cases} 2(\mathbf{c}_B - \mathbf{c}_A) & t < \tfrac{1}{2} \\[2pt] 2(\mathbf{c}_C - \mathbf{c}_B) & t > \tfrac{1}{2} \end{cases} \]

These are not equal in general, so the function is not $C^1$: there's a kink at the midpoint. In a still image of a sky gradient that kink is invisible to the eye because the colors are close. If you cranked the colors apart (e.g. red → black → blue) you'd start to see the seam as a faint horizontal banding.

3.3 GLSL mix = lerp

Just to nail it down:

\[ \operatorname{mix}(\mathbf{a}, \mathbf{b}, t) = \mathbf{a}(1 - t) + \mathbf{b}\,t \]

This is the same lerp from Guide 03, applied component-wise to vec3 colors. mix(red, blue, 0.0) = red; mix(red, blue, 1.0) = blue; mix(red, blue, 0.5) = (red + blue) / 2. It also works on scalars and on vec2, vec4.

3.4 Radial smoothstep falloff

A point sprite in WebGL is a square: when you draw a THREE.Points object, each vertex becomes a small axis-aligned quad of size gl_PointSize pixels. The fragment shader runs over that whole square. To make a star look round and soft instead of square and sharp, the project applies a radial falloff.

The fragment's UV inside the sprite is gl_PointCoord, ranging from $(0,0)$ at the top-left corner to $(1,1)$ at the bottom-right. Centering it gives a coordinate measured from the sprite's middle:

\[ \mathbf{p} = \mathtt{gl\_PointCoord} - (0.5,\, 0.5) \in [-0.5, 0.5]^2 \]

Its length is the radial distance from the center:

\[ d = \lVert\mathbf{p}\rVert \in [0,\, \sqrt{0.5}] \approx [0,\, 0.707] \]

The corners are at $d \approx 0.707$, the edge-midpoints at $d = 0.5$, the center at $d = 0$.

The project's falloff line is:

float falloff = smoothstep(0.5, 0.1, dist);

Two things are happening here. First, the smoothstep ramp from Guide 03:

\[ \operatorname{smoothstep}(e_0, e_1, x) = \begin{cases} 0 & x \le e_0 \\ 3s^2 - 2s^3,\;\; s = \tfrac{x - e_0}{e_1 - e_0} & e_0 < x < e_1 \\ 1 & x \ge e_1 \end{cases} \]

Second, the project passes the edges in reversed order: edge0 = 0.5, edge1 = 0.1. GLSL doesn't object — the formula still works as written — but the practical effect is to flip the ramp. With $e_0 = 0.5$ and $e_1 = 0.1$:

  • For $d \ge 0.5$ (near and beyond the sprite's edge): falloff = 0.
  • For $d \le 0.1$ (the bright core): falloff = 1.
  • For $0.1 < d < 0.5$: a smooth $1 \to 0$ rolloff.

So the result is “1 near the center, 0 at the edge, smooth transition between.” This is the outer-to-inner convention: read the call as “the outer edge is 0.5 (where the star ends), the inner edge is 0.1 (where the bright core begins).”

You could equivalently write 1.0 - smoothstep(0.1, 0.5, dist). The reversed-edge form is shorter and produces identical pixels.

3.5 Putting it together: the starfield fragment

The full per-star color, assembled from the pieces above, is:

\[ \mathbf{c}_\text{out} = \mathbf{c}_\text{tinted} \cdot \mathrm{intensity}, \qquad \mathrm{intensity} = b \cdot \tau(t) \cdot f(d) \]

where

  • $\mathbf{c}_\text{tinted} = \operatorname{mix}(\mathbf{c}_\text{warm}, \mathbf{c}_\text{cool}, \mathtt{vTint})$ — the per-star color, lerped between two palette endpoints by a per-vertex tint attribute.
  • $b = \mathtt{vBrightness}$ — per-vertex brightness in $[0.5, 1.0]$.
  • $\tau(t)$ — the twinkle factor (Guide 14 will derive this from sin).
  • $f(d)$ — the radial smoothstep falloff from above.

The output also writes intensity to the alpha channel so that the additive blending mode can softly fade each star into the background. We'll defer twinkle and additive blending to Guide 14; for this guide, treat $\tau(t)$ as a constant 1.

4. In this codebase

Now read the project shaders with the math in hand. From src/skybox/gradient-mesh.ts:

export const GRADIENT_VERTEX_SHADER = /* glsl */ `
  varying vec3 vDirection;
  void main() {
    vDirection = position;
    gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
  }
`;

Per-vertex breakdown:

  1. Three.js gives us the cube's vertex position (one of the 8 corners scaled by the BoxGeometry(2, 2, 2) — so each component is $\pm 1$).
  2. We assign that raw position to the varying vDirection. The GPU will linearly interpolate it across each triangle, giving every fragment its own vDirection — effectively, the world-space ray from the cube's center to that fragment.
  3. We compute the standard clip-space position so the GPU knows where to draw.

The fragment shader is where the math from §3.1–3.3 lives:

export const GRADIENT_FRAGMENT_SHADER = /* glsl */ `
  precision mediump float;
  uniform vec3 uColorA;
  uniform vec3 uColorB;
  uniform vec3 uColorC;
  uniform vec3 uDirection;
  varying vec3 vDirection;

  void main() {
    float t = dot(normalize(vDirection), normalize(uDirection)) * 0.5 + 0.5;
    vec3 color = t < 0.5
      ? mix(uColorA, uColorB, t * 2.0)
      : mix(uColorB, uColorC, (t - 0.5) * 2.0);
    gl_FragColor = vec4(color, 1.0);
  }
`;

Line by line:

  • float t = dot(normalize(vDirection), normalize(uDirection)) * 0.5 + 0.5; — the affine-remapped cosine from §3.1.
  • The ternary is the piecewise mix from §3.2: lerp $A \to B$ on the bottom half, $B \to C$ on the top half.
  • vec4(color, 1.0) packs the RGB with full alpha. The cube is drawn with side: THREE.BackSide (see gradient-mesh.ts:76) so we paint the inside walls.

The colors come from CSS variables, briefly. src/skybox/css-color.ts reads them via getComputedStyle and falls back to hard-coded defaults if the variable is unset:

export function readCssColor(name: string, fallback: string): THREE.Color {
  const raw = getComputedStyle(document.documentElement).getPropertyValue(name).trim();
  return new THREE.Color(raw || fallback);
}

The fallbacks for the gradient (from gradient-mesh.ts:22) are "#2a1a10", "#3d2414", "#5c3420" — the warm desert browns you see if no CSS variables are defined. We'll use these in the worked examples.

From src/skybox/starfield-skybox.ts, lines 53–61 are the heart of the falloff math:

void main() {
  vec2 centered = gl_PointCoord - vec2(0.5);
  float dist = length(centered);
  float falloff = smoothstep(0.5, 0.1, dist);
  float twinkle = 0.7 + 0.3 * sin(uTime * uTwinkleFreq + vPhase);
  float intensity = vBrightness * twinkle * falloff;
  vec3 color = mix(uColorWarm, uColorCool, vTint);
  gl_FragColor = vec4(color * intensity, intensity);
}

The falloff is exactly the construction from §3.4. The color = mix(uColorWarm, uColorCool, vTint) uses GLSL's mix on a vec3 — a per-component lerp between two color endpoints, just like §3.3.

6. Worked examples

Example 1 — gradient at the “top” with $\hat{\mathbf{u}}$ pointing straight up

Use the project fallback colors:

  • $\mathbf{c}_A = \mathtt{\#2a1a10} = (42, 26, 16) / 255 \approx (0.165,\, 0.102,\, 0.063)$
  • $\mathbf{c}_B = \mathtt{\#3d2414} = (61, 36, 20) / 255 \approx (0.239,\, 0.141,\, 0.078)$
  • $\mathbf{c}_C = \mathtt{\#5c3420} = (92, 52, 32) / 255 \approx (0.361,\, 0.204,\, 0.125)$

Take $\hat{\mathbf{d}} = \hat{\mathbf{u}} = (0, 1, 0)$. Then

\[ \hat{\mathbf{d}} \cdot \hat{\mathbf{u}} = 1, \qquad t = 1 \cdot 0.5 + 0.5 = 1.0 \]

Since $t \ge 0.5$ we use the right branch with parameter $2(t - 0.5) = 1.0$:

\[ \mathbf{c} = \operatorname{mix}(\mathbf{c}_B, \mathbf{c}_C, 1.0) = \mathbf{c}_C \approx (0.361,\, 0.204,\, 0.125) \]

So the topmost pixel is exactly color C, $\mathtt{\#5c3420}$.

Example 2 — same axis, fragment on the equator

Same colors and gradient axis $\hat{\mathbf{u}} = (0, 1, 0)$. Now $\hat{\mathbf{d}} = (1, 0, 0)$:

\[ \hat{\mathbf{d}} \cdot \hat{\mathbf{u}} = 0, \qquad t = 0 \cdot 0.5 + 0.5 = 0.5 \]

This is the seam between the two branches. Either branch gives the same answer (by §3.2's continuity check):

\[ \mathbf{c} = \operatorname{mix}(\mathbf{c}_A, \mathbf{c}_B, 1.0) = \mathbf{c}_B \approx (0.239,\, 0.141,\, 0.078) \]

Equivalently $\operatorname{mix}(\mathbf{c}_B, \mathbf{c}_C, 0.0) = \mathbf{c}_B$. The horizon is exactly color B.

Example 3 — falloff at three radii

With smoothstep(0.5, 0.1, dist), evaluate at $d = 0.1$, $d = 0.3$, $d = 0.5$.

Recall: smoothstep(e0, e1, x) = 0 if $x \le e_0$ when $e_0 > e_1$ is interpreted via the same formula; you get 0 when $(x - e_0)/(e_1 - e_0) \le 0$ and 1 when that ratio is $\ge 1$. Let's compute $s = (x - e_0)/(e_1 - e_0) = (d - 0.5)/(0.1 - 0.5) = (0.5 - d)/0.4$.

  • $d = 0.1$: $s = 0.4 / 0.4 = 1.0 \Rightarrow f = 1$. The bright core.
  • $d = 0.3$: $s = 0.2 / 0.4 = 0.5 \Rightarrow f = 3(0.25) - 2(0.125) = 0.75 - 0.25 = 0.5$. Half intensity.
  • $d = 0.5$: $s = 0.0 \Rightarrow f = 0$. The sprite edge.

So a pixel halfway between the core and the edge has exactly half the brightness of the core — a useful sanity check.

7. Exercises

  1. Routine. With the project fallback colors and gradient direction $\hat{\mathbf{u}} = (1, 0, 0)$, compute the gradient color at $\hat{\mathbf{d}} = (1, 0, 0)$ and at $\hat{\mathbf{d}} = (-1, 0, 0)$. Express each as a normalized RGB triple.
  2. Routine. The default project gradient direction is (1.0, 0.6, 0.4) (see gradient-mesh.ts:23). Normalize it. Then compute the gradient parameter $t$ at $\hat{\mathbf{d}} = (0, 1, 0)$ (the top of the cube).
  3. Routine. For smoothstep(0.5, 0.1, dist), find the distance $d$ at which the falloff reaches exactly $0.25$.
  4. Conceptual. Why does the project use $0.5 \cdot \mathbf{d}\cdot\mathbf{u} + 0.5$ rather than $\lvert \mathbf{d}\cdot\mathbf{u} \rvert$? Sketch (in words) how the gradient's color order would change if you replaced the affine remap with the absolute value. Hint: think about what happens at $\hat{\mathbf{d}} = -\hat{\mathbf{u}}$.
  5. Conceptual. The fragment shader normalizes vDirection per fragment. vDirection comes from the cube's vertex positions interpolated across the face. If we instead pre-normalized at vertices and let the GPU interpolate the unit vectors (skipping the per-fragment normalize), would the result be exactly the same? Briefly: why or why not?
  6. Project-applied (extension). Suppose the project replaced the three-stop piecewise mix with a single $C^1$ Hermite curve through $\mathbf{c}_A$ at $t = 0$, $\mathbf{c}_B$ at $t = 0.5$, $\mathbf{c}_C$ at $t = 1$ (one continuous cubic per channel, no kink at $t = 0.5$). Describe the visual difference you'd expect when colors A, B, C are far apart, and when they are close (like the project's defaults). Which scenario benefits more?
  7. Project-applied (extension). The starfield uses smoothstep(0.5, 0.1, dist). If you tightened it to smoothstep(0.45, 0.35, dist), what happens to the perceived size of stars? What about smoothstep(0.5, 0.5, dist) (zero-width transition)? Sketch the curves mentally; you can verify in the playground.

9. Appendix: Solutions

Exercise 1

With $\hat{\mathbf{u}} = (1, 0, 0)$:

  • $\hat{\mathbf{d}} = (1, 0, 0)$: dot $= 1$, $t = 1$. Right branch, $\operatorname{mix}(\mathbf{c}_B, \mathbf{c}_C, 1) = \mathbf{c}_C \approx (0.361,\, 0.204,\, 0.125)$.
  • $\hat{\mathbf{d}} = (-1, 0, 0)$: dot $= -1$, $t = 0$. Left branch, $\operatorname{mix}(\mathbf{c}_A, \mathbf{c}_B, 0) = \mathbf{c}_A \approx (0.165,\, 0.102,\, 0.063)$.
Exercise 2

$\mathbf{u} = (1.0, 0.6, 0.4)$. Magnitude $\lVert\mathbf{u}\rVert = \sqrt{1 + 0.36 + 0.16} = \sqrt{1.52} \approx 1.2329$. So

\[ \hat{\mathbf{u}} \approx (0.811,\, 0.487,\, 0.324) \]

At $\hat{\mathbf{d}} = (0, 1, 0)$, the dot is $0.487$, so $t \approx 0.487 \cdot 0.5 + 0.5 = 0.7435$.

(That's in the upper branch; you'd then mix $\mathbf{c}_B \to \mathbf{c}_C$ with parameter $2(0.7435 - 0.5) = 0.487$, yielding a point about 49% of the way from B to C.)

Exercise 3

We need $f(d) = 0.25$, where $f = s^2(3 - 2s)$ and $s = (0.5 - d)/0.4$.

Solve $s^2(3 - 2s) = 0.25$, i.e. $2s^3 - 3s^2 + 0.25 = 0$. By inspection or the substitution $s \to 1 - s'$ (smoothstep is symmetric about $s = 0.5$), the solution in $(0, 1)$ closer to $0$ is $s \approx 0.3139$. Then

\[ d = 0.5 - 0.4 \cdot s \approx 0.5 - 0.4 \cdot 0.3139 \approx 0.374 \]

(There's a second solution near $s \approx 1 - 0.3139 = 0.686$, i.e. $d \approx 0.226$, where the curve is already past its inflection. Both are mathematically valid roots; for the smoothstep ramp the relevant one is the first.)

Exercise 4

The remap $0.5 \cdot \mathbf{d}\cdot\mathbf{u} + 0.5$ is monotonic in the dot product: $-1 \mapsto 0$ and $+1 \mapsto 1$ are distinct ends. So $\hat{\mathbf{u}}$ and $-\hat{\mathbf{u}}$ map to opposite colors ($\mathbf{c}_A$ vs $\mathbf{c}_C$).

$\lvert \mathbf{d}\cdot\mathbf{u} \rvert$ is symmetric: $-1$ and $+1$ both map to $1$, and $0$ maps to $0$. So the gradient axis would be doubled — both poles would be color C, the equator would be color A, and B would sit at the dot product $\pm 0.5$. You'd lose the “sky vs ground” asymmetry that the affine remap is designed to give.

Exercise 5

Not exactly the same. Linearly interpolating the components of two unit vectors does not in general yield a unit vector at the interior point: $\operatorname{mix}(\hat{\mathbf{a}}, \hat{\mathbf{b}}, 0.5)$ has length $\le 1$ (with equality only when $\hat{\mathbf{a}} = \hat{\mathbf{b}}$). So skipping the per-fragment normalize would shorten the interpolated direction, biasing the dot product (and therefore $t$) toward 0.5 in the middle of each face. The visible effect is a slight over-contraction of the gradient's middle band. The project's per-fragment normalize is the cheapest cure.

Exercise 6

A $C^1$ cubic kills the slope discontinuity at $t = 0.5$. When colors A, B, C are far apart (e.g. red, black, blue), the kink in the piecewise mix shows up as a faint horizontal seam at the equator; the cubic erases it, giving a more painterly transition. When colors are close (the project's earthy #2a1a10 / #3d2414 / #5c3420), the slope jump is so small relative to display gamut and dithering that it's invisible — the cubic gives essentially no perceptual win and costs an extra few multiplies per fragment. Far-apart colors benefit; close colors don't.

Exercise 7

smoothstep(0.45, 0.35, dist): zero-falloff zone widens (0 outside $d = 0.45$, 1 inside $d = 0.35$, transition only across a $0.10$-wide band). Stars look smaller and harder-edged — less halo, more dot.

smoothstep(0.5, 0.5, dist): the transition width is zero. GLSL's smoothstep with $e_0 = e_1$ is degenerate; in practice (and per spec, with division by zero) you'd get a step function — 0 for $d > 0.5$, 1 for $d < 0.5$. You'd see hard-edged disks: round but no smooth halo. Aesthetically: stars stop twinkling-feeling and start looking like printed dots.
